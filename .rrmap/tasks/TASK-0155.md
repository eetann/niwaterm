## 前提が崩れた点（実測で判明）

**niwaterm側から画面の位置を触る余地が無い。** Claude Codeはalternate screenで動き、会話は
niwatermのスクロールバックに1行も残らない。libghostty-vtのtracked grid refを使っても、
追従先のセルの中身が次のフレームで別物になるため意味を持たない。設定ファイルのhooksからも
画面には触れない（hookのプロセスは制御端末を持たず`/dev/tty`へ書けない）。
詳細はdocs/known-issues/claude-code-history-not-in-scrollback.md。

一方で**Claude Code自身はスクロールを持っている**（`PageUp`/`PageDown`・`ctrl+Home`・
`ctrl+End`）。つまり「飛ぶ」は諦めなくてよく、Claude Codeに頼んで動かす形になる。

## 決めたこと

**目次はniwaterm側のUI（hoverButtons）で描き、Claude CodeのTUIの中には何も出さない。**
ジャンプだけをClaude Codeのmod（function hooks）の`$.ui.scroll`へ頼む。

画面の文字列を`tab capture`で照合しながら`PageUp`を送る方式も実測では動いたが、
描画の変化に弱い画面スクレイピングになるので採らない。

**合図はキー送信。** transcriptの行を動かせるのは人の操作に応えている間だけで、タイマーや
通知から呼ぶとengineが`deny: "not person-initiated"`で弾く。そのためniwatermはタブ変数
`agent_jump`へジャンプ先を書いてからキーを送り、mod側のButtonの押下として受け取らせる。
Buttonは`display: "none"`でも押せるので、Claude Codeの画面には1行も出ない。
スラッシュコマンド・`prompt.submit`の横取りでも動いたが、前者はtranscriptに行が残り、
後者は入力欄が空でないと下書きに混ざる。

**プロンプト行の`requestId`はtranscript（jsonl）のuuidと同じ値だった。** niwatermが
`claude prompt list`で見せている一覧の値をそのまま渡せるので、画面との突き合わせは要らない。

**サイドバーの会話ビューア（customView）は作らない。** 目次から飛べるなら要らないため。
CLIの`claude prompt list` / `show`はエージェントからの参照用に残す。

## 引き継ぎ

- function hooksは早期アクセス扱い（`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`が必要、
  Claude Code 2.1.260以降）。上げてジャンプが効かなくなったらmod側のAPIを疑う
- modの`action`はengineのキーバインドアクションを借りる形で、**engineがそのアクションを
  処理できる状態だとengine側が優先する**。既定の`app:openArtifact`はartifactが開ける場面では効かない
- Codex CLIのhook入力に会話記録のパスが入るかは未調査。入るなら`agentTranscript`の分岐へ
  足すだけで目次までは同じものが使える（ジャンプはCodex側に相当するAPIが要る）
- 合成マウス入力での検証は、クリックのたびにniwatermのウィンドウが前面にあることを
  確かめること。裏に回ると別ウィンドウを押してしまい「1番目しか反応しない」ように見える
