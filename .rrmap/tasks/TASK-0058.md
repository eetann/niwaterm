TASK-0057（WebView2 UserDataFolder衝突）の実機検証中（2026-08-26）に発覚。TASK-0056で
「project_root（ディレクトリ）を分離すればビルドロックは回避できる」としていたが、
それとは別レイヤーのグローバルロックが存在し、実体分離だけでは解決しない。

## 症状

`niwaterm-wip`（`niwaterm-worktrees/niwaterm@dev`）で`mise run start`（`electrobun dev`）を
起動した状態で、別ディレクトリの`niwaterm-daily`（`niwaterm-worktrees/niwaterm`）でも
`mise run start`を実行すると、後発側のビルドが**preBuildの実行にすら到達せず**完全に
スタックする（該当ディレクトリの`build/`配下が一切更新されない。hutch-engine.exeのCPU時間も
起動直後から増加が止まる）。

## 原因

`electrobun dev`はビルドツールHutch（`~/.hutch/npm/electrobun/2.0.1/windows-x64/bin/`に
インストールされる別プロダクト、クローズドソース版がnpm経由で配布されている。ソース自体は
`blackboardsh/hutch`にGitHub公開されている、Zig実装）を経由して動く。Hutchは
`~/.hutch/state/locks/graph.lock`という**プロジェクト単位ではなくユーザー単位でグローバルな**
ロックファイルを使っている。

当初「`electrobun dev`はプロセスが生きている間このロックを占有し続ける」と推測していたが、
2026-08-26の追加実機検証でこれは不正確だったと判明（詳細は下記「実機再検証」節）。
正しくは、単体のdevプロセスはアイドル時（watchループでの待機中）は`graph.lock`を解放しており、
**別のHutchプロセス（devでもbuildでも）が新たに起動を試みたときにだけ、その後発側の起動処理
自体が完全に停止し、その間だけ`graph.lock`がLOCK HELD状態になる**。先発側を停止すると
後発側は待たされていた分の遅延なく即座に動き出す。つまり「devモードだから常時ロックを
保持する」のではなく、「Hutchの複数インスタンスが同時に存在すると、後から来た側の起動処理
自体がグローバルな何かを介して直列化され、先発側が生きている間ブロックされ続ける」という
設計・挙動が実体に近い。

blackboardsh/electrobunのGitHub issueには該当するものが見当たらなかった（`gh search issues`で
hutch lock/graph.lock/concurrent/simultaneously/dev stuck等を検索。Hutch自体が別プロダクトで
electrobunリポジトリにソースがないため、issueとして報告されていてもelectrobun側では
ヒットしない可能性がある）。`blackboardsh/hutch`リポジトリ自体も検索したが、issueは
1件のみ（`lightningcss`インストール失敗の報告、ロックとは無関係）で、グローバルロックに
関する既知の報告は見当たらなかった。

## 実機再検証（2026-08-26、未調査項目の消化）

dailyには一切触れず、Windows側だけにwipのコピー（project_rootのみ分離したテスト用ディレクトリ
`niwaterm-worktrees/niwaterm-locktest`、`NIWATERM_APP_NAME=niwaterm-locktest`でidentifier等も
分離）を作って安全に競合を再現した。

1. **単体devプロセスのアイドル時、`graph.lock`は解放されている**: wipのみを`electrobun dev`で
   起動し、ビルド完了後（"niwaterm started"ログ確認後）に`graph.lock`へ`[System.IO.File]::Open
   (...,'None')`で5回連続プローブしたが、常にLOCK FREEだった。ファイル変更を加えて再ビルドを
   トリガーした直後（40回×約180msの高頻度プローブ）も一貫してLOCK FREE。つまり本タスク作成時に
   書いた「起動中は常に保持される」という記述は誤りだった（当時はwip/daily同時起動という
   条件下での観察だったため、後発側がブロックされている状態を「先発側が保持し続けている」と
   誤認していた可能性が高い）。
2. **project_root分離済みでも、後発側の起動そのものが完全に停止する**: wip起動中に
   `niwaterm-locktest`で`electrobun dev`を起動すると、`preBuild`にすら到達せず
   `hutch-engine.exe`のCPU時間も増加が止まった（TASK-0058本文の症状と同一の再現に成功）。
   この間`graph.lock`は一貫してLOCK HELD。**wip側のdevプロセスをkillした瞬間、locktest側の
   ビルド〜起動ログが一気に流れて即座に完了し、`graph.lock`も即座にLOCK FREEに戻った**。
   これは「先発側が生きている限り後発側がブロックされ続け、先発側が消えた瞬間に後発側が
   前進する」という直接的な因果関係を示す一次証拠。
3. **devモード特有ではなく、`electrobun build`（単発ビルド、`--watch`なし）でも同一現象が
   発生する**: locktestを`electrobun dev`で起動したままwip側で`bun x electrobun build`
   （devサブコマンドではなくbuildサブコマンド）を実行したところ、60秒待っても完了せず
   プロセスが残り続けた（`graph.lock`もLOCK HELD）。locktest側を停止した瞬間、wipの
   `electrobun build`側も即座に完了した。よって未調査項目「devモード特有かbuild含めて
   共通か」は**build含めて共通**と判明。
4. Hutchソース（Zig実装、`store_locks.zig`/`managed_store.zig`）を読むと、`graph.lock`自体は
   `acquireGraph`で`.shared`モードで取得され、`prepareProject`等の呼び出し元は関数スコープの
   `defer`で毎回すぐ解放する設計に見える（実機観察1と整合）。一方`~/.hutch/state/locks/
   projects/<project_rootのSHA256ハッシュ>.lock`という、project_root単位だがユーザーホーム
   配下に置かれる別系統のロックファイルも存在する（`managed_store.zig`の
   `projectRegistrationLockPath`、"project registration"＝自動プルーニング対象外登録に
   関連するものと推測）。後発側が正確にどの処理・どのロック取得でブロックされているか
   （`graph.lock`自体の取得待ちなのか、プロジェクト登録処理なのか、Cottontailサブプロセス
   起動時の何らかの共有リソース競合なのか）は未特定。ソースはZigの`std.Io`非同期I/O層を
   使っており、Windows特有のロック実装（`file_locks.zig`のコメントに「Zig 0.16's Windows
   blocking lock path does not handle STATUS_PENDING」という既知の制約への言及あり）に
   起因するWindows限定のバグである可能性も残る（macOS/Linuxでの再現は未検証）。

## 回避策（確認済み・タスク化済み）

ビルド済みバイナリ（`<worktree>\build\<app>\dev-win-x64\<app>-dev\bin\launcher.exe`）を
`electrobun dev`を経由せず`Start-Process`で直接実行すれば、`graph.lock`の影響を受けずに
wip/dailyを同時起動できることを確認した（2026-08-26実機検証、TASK-0057の再検証時）。
事前に両方とも`electrobun dev`で単体ビルドを完了させておき、その後`mise run win:stop`で
devプロセスを止めてから`launcher.exe`を直接起動する、という手順になる。

2026-08-26、`mise run win:start:built`として恒久タスク化した（mise.toml）。現在のブランチから
wip/dailyを自動判定し（`win:stop:mine`と同じロジック）、対象の`launcher.exe`が存在しなければ
「先に`mise run start`でビルドしてください」というエラーで案内して終了する。既存の
`win:stop`/`win:stop:mine`でそのまま停止できることも実機確認済み（`win:stop`は元々
`ProcessName -match 'bun|electrobun|hutch'`で`launcher`を含んでおらず、`launcher.exe`単体では
取りこぼす可能性があったため、ついでに正規表現へ`launcher`を追加した）。実機での動作確認手順：
1. wipで`mise run win:start:built`起動 → `hutch.exe`/`hutch-engine.exe`を経由せず
   `launcher.exe`/`bun.exe`のみが起動することを確認
2. `mise run win:stop:mine`で正しく停止することを確認
docs/build/windows-build.md・CLAUDE.mdにも案内を追記した。

## 未調査（残）

- 後発側が正確にどの処理でブロックされているか（`graph.lock`自体の取得待ちか、
  `~/.hutch/state/locks/projects/*.lock`のプロジェクト登録処理か、Cottontailサブプロセス
  起動時の別の共有リソース競合か）。実用上は回避策があるため優先度は低い

## 運用上の影響

wip・dailyを`mise run start`（devモード）で同時起動することはできない。同時に動作確認したい
場合は、両方を**順番に**`mise run start`でビルド完了させてから`mise run win:stop:mine`で止め、
それぞれで`mise run win:start:built`を使ってビルド済みの`launcher.exe`を直接起動する
（同時にビルドさせないこと。ホットリロードは失われる）。
