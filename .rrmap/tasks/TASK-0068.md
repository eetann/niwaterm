次のような`█`を使った文字が上下に並ぶと、weztermとかだと隙間無く並ぶけど、niwatermだと隙間がある
```txt
 ▐▛███▛█   Claude Code v2.1.251
▝▜██████▀  Opus 5 with xhigh effort · Claude Pro
  ▝▝ ▝▝    ~/ghq/github.com/eetann/rrmap
```
`cat .rrmap/tasks/TASK-0068.md`してスクショ取ると隙間が分かる

## 原因

フォントの`█`のグリフはfont-size基準の高さしか持たないのに対し、行ボックスの高さは
lineHeight（デフォルト: fontSize=13pxに対して18px）。その差＝行間の分だけ、
上下に並んだブロック文字の間に地の背景色が見える。
weztermやGhosttyはこの手の文字をフォントのグリフではなくセル矩形へ直接描画するため隙間が出ない。

## 方針・実装

セル矩形いっぱいに描かれる前提の文字（U+2500-257F 罫線素片 / U+2580-259F ブロック要素 /
U+1FB00-1FBFF レガシー計算記号）を、行の高さいっぱいへ引き伸ばす。

- src/mainview/cell-glyph.ts — 対象文字の判定と、`█`のインク矩形を行ボックスへ写す
  縦方向の相似変換の計算（純粋関数、テストあり）
- src/mainview/index.ts — `█`のインク矩形をcanvasの`measureText`で、行ボックス上端から
  ベースラインまでの距離を空のinline-blockのベースライン規定を使ったDOM実測で取り、
  変換をCSS変数(`--cell-glyph-scale`/`--cell-glyph-shift`)へ入れる（applyAppearanceから測り直す）。
  fixWideChars改めfixGlyphsが、連続する対象文字をまとめて`<span class="cell-glyph">`でラップする
- src/mainview/index.css — `.cell-glyph`にinline-block + transformを適用

フォントが変わっても実測ベースなので追従する。測定に失敗した場合や倍率が異常な場合は
恒等変換へフォールバックし、ラップ自体も行わない。

Powerlineのセパレータ(U+E0B0-)も同じ問題を持つが、私用領域でフォントごとに
デザインが違い`█`と同じ矩形を前提にできないため対象外にした。
