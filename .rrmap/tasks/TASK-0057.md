TASK-0056（ビルドロック対策のworktree分離）の実機検証中（2026-08-26）に発覚。ビルドロック自体は
worktree分離で解消したが、それとは別レイヤーの問題。

## 症状

niwaterm-wip・niwaterm-dailyのどちらか一方が既に起動している状態で、もう一方を起動すると、
**後から起動した方**のウィンドウでサイドバーの中身・タイル/ターミナル表示が一切描画されない
（`<div id="tile-tree">`等のDOM骨格は存在するが空。`sidebar`要素自体が存在しないこともある）。
プロセス自体はクラッシュせず起動したまま（`Responding: True`）。

再現した2パターン:
- daily起動時にwipが先に動いていた → dailyのapp.logに`[WebView2] ERROR: Controller is NULL,
  cannot resize`が記録され、その後何も描画されない
- wip起動時にdailyが先に動いていた → app.logに上記エラーすら出ず、`NavigationStarting`の後
  `NavigationCompleted`に相当するログが一切出ない（Navigation自体が完了していない様子）

一方、他方が起動していない単体起動では、同じ`Controller is NULL`エラーが出ても
自己回復して正常に表示されることを確認した（daily単体で1回確認）。

## 原因（identifier固定は修正したが主症状は未解決。実機再検証で判明）

2026-08-26の実機再検証で、identifier分離（下記）はWebView2のUserDataFolder自体を
完全に分離できていることを確認した（`Get-CimInstance Win32_Process`でWebView2
レンダラープロセスのコマンドラインを見ると、wipは
`AppData\Local\dev.eetann.niwaterm-wip\dev\WebView2\...`、dailyは
`AppData\Local\dev.eetann.niwaterm-daily\dev\WebView2\...`と別パスになっている）。

**しかしそれでも、wip起動中にdailyを起動すると後発のdaily側が真っ白のまま描画されず、
5分待っても自己回復しなかった**（`app.log`が`setJSUtils`〜`Controller is NULL, cannot
resize`の手前で完全に停止、それ以降のログが一切出ない）。つまりUserDataFolderの
衝突は本タスクの症状の一因ではあったが、**主原因ではなかった**。WebView2ランタイム
自体（レンダラープロセス共有、GPU関連リソース等）の複数インスタンス初期化競合という、
niwaterm側のidentifier設定では解決できない、より低レイヤーの要因が残っている。

この再検証は`electrobun dev`のグローバルビルドロック（[[TASK-0058]]参照）を回避するため
`launcher.exe`を直接起動する形で行った。`electrobun dev`経由の起動（コンソールアタッチ・
watchあり）とは初期化パスが多少異なる可能性があるが、TASK-0057最初の発見時の症状
（後発側描画なし、`Controller is NULL`、自己回復しないケースがある）と一致しており、
再現性は確認できたと判断している。

## 原因調査の経緯（identifier固定・electrobun.config.tsのidentifier固定）

Electrobun本体（`package/src/native/shared/app_paths.h`・`windows_profile_paths.h`）を読むと、
Windows版のWebView2用UserDataFolderは`%LOCALAPPDATA%/<identifier>/<channel>/WebView2`という
式のみで決まり、**アプリ名（`name`）はこのパスに一切反映されない**。ところがniwatermの
`electrobun.config.ts`では`identifier: "dev.eetann.niwaterm"`がwip/dailyで共通の固定文字列
だった（`NIWATERM_APP_NAME`で変わるのは`name`のみ）。channelも明示指定なしで両方"dev"。
つまりniwaterm-wipとniwaterm-dailyは、WindowsのWebView2の実データ（UserDataFolder）を
完全に共有していた。WebView2は同じUser Data Folderを複数プロセスが同時に開くことを
想定しておらず、後発プロセスの環境生成がロック競合で不安定になる——というのが本タスクの
症状（後発側だけ描画されない、`Controller is NULL`、自己回復するときとしないとき）と符合する。

blackboardsh/electrobunのGitHub issueには直接該当するものは見つからなかった（`gh search issues`
でmultiple instance/WebView2/Controller is NULL等を検索。electrobun自体のバグというより
niwaterm側の設定不備）。

対応: `electrobun.config.ts`の`identifier`を`` `dev.eetann.${appName}` ``に変更し、
アプリ名ごとに分離した（Windows通知のAUMID用に`src/bun/windows-notification.ts`が既に
`` `dev.eetann.${APP_VARIANT}` ``という同じ設計のIDを使っていたので、その形式に揃えた）。

## WebView2 Runtime自体の既知issue（2026-08-26調査）

`MicrosoftEdge/WebView2Feedback#2703`「Creating Multiple WebView2 Instances causes
0x8007139f error on one Instance」が症状と一致する。Microsoft担当者の回答：**複数の
WebView2アプリをほぼ同時に起動すると、WebView2 Runtime内部のレースコンディションで
片方の`CreateCoreWebView2ControllerAsync`が`ERROR_INVALID_STATE`(0x8007139f)で失敗する。
「2つ目の起動を少し遅らせれば回避できる」とのことだが、2022年に修正が入りRuntime 106
リリースで提供されたはずのバグ**。関連する`#4731`（Windows Server限定、2024年報告）は
「Desktop OSでは再現しない」とされているため、niwatermの症状がこれと全く同じ根本原因か
は未確定。Runtime内部のバグのため、恒久修正はniwaterm/electrobun側の手が届かない。
成功時のコールバック自体が二度と呼び出されない（後述）ことを考えると、「自己回復に
数秒〜数十秒かかるレースコンディション」というより「Runtime内部のグローバルなロック
状態が壊れて詰む」種類の失敗に近い可能性がある。

さらにElectrobun本体のソース（`nativeWrapper.cpp`）を読むと、「`Controller is NULL`」
というログは、`CreateCoreWebView2Controller`の非同期コールバックがまだ設定していない
時点で`resize()`が呼ばれた際に出る単純な状態ログ（`if (controller) {...} else {
::log("[WebView2] ERROR: Controller is NULL, cannot resize"); }`）で、通常は後続で
自然に解消されるはずのもの。一方、コントローラー作成のコールバック自体
（`CreateCoreWebView2Controller`の第2引数のラムダ）は、失敗時に`HRESULT`付きの
別ログ（`"ERROR: Failed to create WebView2 controller, HRESULT: 0x%08X"`）を出す設計に
なっている。今回の実機再検証でも後発側にこのログは一度も出ておらず、**コールバック
自体が呼ばれていない**（成功も失敗も）ことを示している。また、Electrobun側には
`ERROR_INVALID_STATE`を検知して`CreateCoreWebView2Controller`を再試行するロジックは
存在しない（WebView2Feedback#2703でMicrosoftが提示している回避策）。

## 実機再検証（2026-08-26、起動タイミングの検証）

dailyには一切触れず、Windows側のみのテスト用project_root（`niwaterm-locktest`、TASK-0058の
時と同じ手法）を使い、`electrobun dev`のグローバルビルドロック（[[TASK-0058]]）を避けて
`launcher.exe`を直接起動する形で検証した（`RedirectStandardOutput`によるログはCランタイムの
フルバッファリングで信頼できず——プロセスが生きている間は書き出されない——実際の判定は
毎回スクリーンショットで行った）。

1. **起動間隔0秒（ほぼ同時）**: wip起動直後にlocktestを起動 → 再現（locktestウィンドウが
   真っ黒のまま）。
2. **起動間隔10秒、かつ先発（wip）が5分以上安定稼働した状態から起動**: それでも再現。
   「タイミングが早すぎた」では説明できない結果になるという本タスクの当初の観察を裏付けた。
   **未調査項目「起動タイミングをずらせば回避できるか」への回答は「回避できない」**。
3. **症状再現後、先発（wip）を停止しても後発（locktest）は自己回復しなかった**。TASK-0058の
   Hutchグローバルビルドロック（先発を止めた瞬間に後発が即座に前進する）とは異なり、
   **一度この状態に陥ると恒久的に壊れたままになる**。単純な「先発が生きている間だけ
   後発を待たせる」直列化ではない。
4. **クリーンな状態（他に何も起動していない）からlocktestを単体起動すると正常に動作した**。
   壊れるのは「もう一方が既に動いている状態で起動した場合」に限る。

## 未調査（残）

- WebView2Feedback#2703の根本原因とniwatermの症状が完全に同一かは未確定（前者は
  「レースコンディション」、後者は「一度発生すると恒久的」という違いがある）
- Electrobun本体へのissue報告・PR提出（`ERROR_INVALID_STATE`時のリトライ実装）を
  するかどうか。niwaterm単体では解決できない、Electrobun本体側の対応が必要な問題
- 単体でも稀に失敗するケースがあるか（今回・TASK-0057発覚時ともサンプル数が少ない）

## 運用上の影響

wip・dailyを同時に起動すると、後から起動した方は高確率で描画されない。**起動タイミングを
ずらしても回避できない**。一度描画されない状態になると、後発側のウィンドウを閉じて
再起動しても直らないことが多い（先発側を含めて両方を再起動する必要がある可能性が高いが
未検証）。同時に動作確認したい場合は、事前にそれぞれ単体で動作確認を終えてから
同時起動を試すか、そもそも同時起動を避けて片方ずつ確認する運用が無難。
