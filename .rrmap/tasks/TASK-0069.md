- ディレクトリに .niwaterm/ があればそれを読み取る
  - configではなく、特定のCLI・API実行時のみ。たとえばレイアウト適用や（今後追加する）ワークツリー関係
- 単にそのディレクトリだけにするか、ワークツリーでメインツリーの方も見るのかは後で決める

## 方針

`.niwaterm/`を「暗黙に環境から探す」のではなく、解決コンテキストを2つに分けて扱う。
これで「Boardが複数ディレクトリを開いているときにどれを読むか」という曖昧さがそもそも発生しない。

### 1. CLI/API実行時（`layout apply`、今後のworktree系）

プロセスのcwdは常に1つなので、そこから上向きに`.niwaterm/`を探せば解決先は一意に決まる。
Board内のタブがいくつのディレクトリを開いていようと無関係。

### 2. 起動時（TASK-0077の`restoreMode: "layout"`）

cwdが存在しないため解決元が決まらない。本質的な課題はここだけ。
**Board内のタブのcwdから推測する方式は採らない**（ユーザーが`cd`すれば変わるため、解決キーとして不安定）。
代わりに、紐づけを作った時点の解決元をBoardへ永続化する。

```ts
// persistence.ts
export interface PersistedBoardStartup {
  preset: string;
  restoreMode: BoardRestoreMode;
  /** プリセットの解決元(絶対パス)。省略時はグローバルconfig */
  projectRoot?: string;
}
```

`layout apply <name> --startup`実行時に`resolveProjectRoot(invocationCwd)`で見つけたルートを記録し、
起動時（index.tsの`applyStartupLayouts`）はそのディレクトリだけを読む。走査も推測も不要。

モデルとしては**1 Board = 1つの出自**。Board内のタブが何のディレクトリを向いていようと、
「このBoardはどのプロジェクトのレイアウトで組まれたか」という事実は1つしかない。
TASK-0077が「Boardが持つのはプリセット名に留めている」と書いた拡張点そのままで、
`名前` → `(root, 名前)`になるだけで済む。

### 解決元の探索は1関数に閉じ込める

`resolveProjectRoot(cwd)`を1つ用意し、layout用もworktree用もここを通す。

1. cwdから上向きに`.niwaterm/`を探す
2. 見つからなければ`git rev-parse --git-common-dir`からメインツリーのルートも見る
   （TASK-0069本文の「ワークツリーでメインツリーの方も見るか」はここで吸収する）

探索ルールが複数箇所に散らばると必ず壊れるので、実装は必ず1箇所にまとめる。

### 名前解決の優先順位

project → global の順で解決し、同名はproject勝ち。ただし`layout list`に出自を表示して
どちらが効いているか分かるようにする（`dev\t[projectA]`）。
曖昧さを嫌うなら`layout apply ./dev`のような明示接頭辞も選択肢だが、まずは優先順位＋表示で足りる想定。

### cwdの相対解決

プロジェクトローカルのプリセットでは`cwd: "./packages/cli"`をprojectRoot相対で解決し、
`cwd`省略時のデフォルトもprojectRootにする（現状はホーム or invocationCwd）。
これでプリセットをリポジトリごと持ち運べる。

### trust prompt（必須）

configは`await import()`でTSを実行する（config.ts）。`.niwaterm/`も同じ方式にするため、
**cloneしたリポジトリのコードが起動時に無条件で走る**。さらにlayout presetの`command`は
シェルを実行する。そのため紐づけを作る操作にtrust promptを挟む。

- 対象: `layout apply <name> --startup` / `board startup layout`のうち、
  プリセットの解決元がプロジェクトローカル（`projectRoot`あり）のとき。
  グローバルconfig由来のプリセットはユーザー自身の設定なのでpromptなし
- 文面: 「このプロジェクトのレイアウトを起動時に適用します。任意のコマンドが実行される
  可能性があるため、信頼できるリポジトリでのみ許可してください」＋対象パスを表示
- 実装は`layout.ts`の`confirmReplace`と同じ形（TTY必須、非対話環境では`failAndExit`して
  スキップ用フラグを案内する）
- **信頼の記録は別ストアを作らず、紐づけ（`startup.projectRoot`の永続化）自体を信頼の記録とする**。
  起動時に自動実行される経路はこの紐づけ1本だけで、それは必ずpromptを通ってしか作られないため
- TASK-0083でサイドバーUIから同じ操作を生やす際も、等価の確認ダイアログが要る

**「Boardを開いたディレクトリのレイアウトを自動適用」のような暗黙の発見には広げない。**
広げる場合はmise/direnv/VSCode workspace trust方式の独立したtrustストアが別途必要になる。

### 失敗時

`projectRoot`が存在しない・`.niwaterm/`が消えた・プリセットが見つからない場合は、
既存の「プリセットが設定に見つかりません」通知パスへ合流させる。骨格は常に保存されているため、
単一タブのまま安全に残せる。

## 実装時に決めたこと

- **ファイル形式・構成**: `<projectRoot>/.niwaterm/config.ts`の1エントリに集約し、
  `NiwatermProjectConfig`（`layouts?`のみ）をdefault exportする。今後のworktree系もこの1ファイルへ
  フィールドを足すだけで済む。`layouts.ts`単体や`.niwaterm/layouts/<name>.ts`分割は採らなかった
- **ランタイムヘルパーを用意しない**: `defineConfig`相当を提供すると`@niwaterm/config`の
  ランタイム解決が必要になり、任意のリポジトリでは解決できない。`import type` + `satisfies`なら
  トランスパイル時に消えるので、node_modulesが無いリポジトリでもそのまま動く
- **trust promptを出す粒度**: 「起動時の自動実行を有効にする操作」ごと。
  `board startup restore`で止めてから`layout`へ戻す場合も再度確認する（解決元の記録は残るが、
  自動実行を再び有効にすることこそガード対象という判断）
- **一度きりの`layout apply`では確認しない**: ユーザーがそのディレクトリで明示的に実行しているため。
  ただし同名プリセットの影に隠れる事故を避けるため、解決元を必ず出力に表示する
  （`layout list`は`[project: <root>]`／`[global]`列、`layout apply`は成功行に付記）
- **内容ハッシュは持たない**: trust後に`git pull`で`.niwaterm/config.ts`が変わっても再確認しない。
  必要になったらmise方式のハッシュを別途検討する

## 実装

- `src/bun/project-config.ts` — `resolveProjectRoot`（上向き探索→gitメインワークツリー）、
  `loadProjectLayouts`、`resolveLayoutPresetByName`、`listResolvedLayouts`、`resolveTabCwd`
- `src/bun/config.ts` — `normalizeLayouts`を切り出して共用。importの一時ディレクトリ管理を
  コピー元パスごとのMapへ変更（グローバル設定と複数プロジェクト設定が世代を消し合わないように）
- `src/bun/persistence.ts` — `PersistedBoardStartup.projectRoot`
- `src/bun/ipc-server.ts` — `/layouts?cwd=`、`/apply-layout`・`/board-startup`の解決とtrust gate
- `packages/cli/src/layout-trust.ts` — y/N確認（非TTYは`--trust`を案内してエラー終了）
- ドキュメント: `docs/guide/cli.md`「プロジェクトローカルのレイアウト」節、`docs/guide/config.md`から相互リンク

サイドバーUIからの操作はTASK-0083（同じ確認ダイアログが必要）。
