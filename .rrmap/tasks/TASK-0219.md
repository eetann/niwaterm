## 調査メモ（2026-11-05時点）

発生環境はmacOS。Windowsでは未遭遇。nvimを閉じた直後にトラックパッドでスクロールしていた記憶あり。

### 混入文字列の正体

- `0;43;21M…64;32;21M…` はSGRマウスレポート（`ESC [ < btn;x;y M/m`）。zleが先頭の`ESC [ <`を食べて残りが文字として入る。64/65=ホイール上下、66/67=横スクロール、0=クリック
- `8;50;190;900;1330t8;12;94;216;658t` はmode 2048（in-band resize通知）のレポート（`ESC [ 48;rows;cols;hpx;wpx t`）。2つのサイズで出ているので、モードが残ったままタブのサイズが2回変わっている
- 「前の表示が残る」はalt screen（`?1049`）から戻れていないためと推測

→ nvim終了時の後始末（`?1049l`・`?1002l`/`?1006l`・`?2048l`）がlibghostty-vt側の状態に反映されていない。マウスエンコーダはghosttyのモードをそのまま見ている（`src/bun/ghostty.ts`の`syncMouseEncoderOptions`）ので、niwaterm側が勝手にレポートを作っている線は薄い

### Windows実機（ConPTY）での実測

Bun.Terminal + wsl.exe(NixOS) + zsh で「`echo` → `C-o` → `:q`」を5回、生バイトを録った

- マウス・alt screenの解除は5回とも届き、`mouseTracking=false`に戻った（再現せず）
- ConPTYはDECRQM（`?2048$p`等）を握りつぶすため、Windowsではnvimが`?2048h`自体を出さない。報告の形はWindowsでは再現しにくい
- 別件: nvimが終了時に出す`?1004l`をConPTYが捨てる（WSL内のLinux PTYでは出ている）。niwatermはフォーカス通知未実装なので実害なし

### nvim 0.12.5の終了時シーケンス（Linux PTYで実測）

`?1002l ?1006l … ?1l ESC> ESC[>4;0m ESC[23;0t ?2004l ?1004l ESC[c ?25h` → zsh側で`?1049l`。
起動時は`?1049h`の直後に`?69$p ?2026$p ?2027$p ?2031$p ?2048$p`、XTGETTCAP、`ESC[?u`、DA1、OSC 11、DSRを問い合わせる

### 次にやること（macOSで）

PTYから読んだバイト列をタイムスタンプ付きでファイルへダンプする一時的な診断コードを入れ、
nvimを閉じた直後にトラックパッドでスクロール／リサイズして再現させる。
「後始末がPTYから届いていない」のか「届いているのにghosttyの状態に反映されていない」のかを切り分ける。
起動時の問い合わせへの応答が遅れて届き、nvimのモード有効化が終了処理と前後する可能性も見る

## 結論

上の推測（解除シーケンスが反映されない）は外れ。原因はnvim終了時ではなく表示中のリサイズで、`pty.resize()`がシェルのグループへ送るSIGWINCHでzshが端末を奪いnvimが停止していた。詳細: docs/known-issues/pty-resize-sigwinch-to-shell-suspends-foreground-job.md
