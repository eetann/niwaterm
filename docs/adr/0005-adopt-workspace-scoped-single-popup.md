# ADR 0005: ポップアップをワークスペース単位・単一インスタンスの独立した状態として位置づける

## Status

Proposed

## Context

niwaterm は Window > Workspace > Tile > Tab の4階層で画面構成を表現している（ADR 0001）。「PTY を保持する単位は Tab、Tile はレイアウト構造のみを担う」というのが既存の定義であり、Tab の中身は現状ターミナル（PTY）が中心で、ブラウザ・customView等も同じ Tab として扱われている。

tmux の popup/floating に相当する機能を追加する計画がある。fzf・lazygit・簡単な動作確認など、タイル分割やタブ作成をせずに一時的なコマンドを実行したいときに使う画面で、cwd指定・実行コマンド指定（終了で自動的に閉じるワンショット実行）・表示サイズ指定に加えて、tmux には無い「後から通常のタブへ昇格できる」「一時的に非表示にして裏のタブへ戻れる」という要件を持つ。

実装に入る前に、この機能が既存の Window/Workspace/Tile/Tab の階層とどう関係するか（「popup とは何か」）を決める必要がある。画面としてどの描画技術（別ウィンドウ・別webview・既存webview内のDOM等）に乗せるかは実装上の選択であり、将来の実装都合で変わりうるため、本ADRのスコープには含めない。

### 解決したい課題

- ポップアップを Tile 木構造の内側（所属タイルを持たない特殊な leaf 等）に位置づけるか、外側の独立した概念にするか
- ポップアップの状態（開いているか・非表示中か）をどの単位（アプリ全体／ワークスペースごと）で持つか、同時に何個まで開けるようにするか
- 「タブへ昇格」を実現する上で、PTY セッションを既存の Tab 管理へ無理なく移せる設計にできるか

### 検討した選択肢

**データモデル上の位置づけ:**

- a. Tile 木構造の中に、所属タイルを持たない特殊な leaf として表現する
- b. Tile 木構造とは独立した、Workspace 直下の別状態として持つ

**同時に開ける数・状態のスコープ:**

- a. アプリ全体で常に1つ、ワークスペースを横断して共有する
- b. ワークスペースごとに独立して最大1つ
- c. ワークスペースごとに複数可

### 各選択肢の評価

データモデル上の位置づけ:

| 観点 | a. Tile木構造内の特殊leaf | b. Workspace直下の独立状態 |
|------|---------------------------|------------------------------|
| 「Tileはレイアウトのみを担う」というADR 0001の定義との整合 | 崩れる（レイアウトに属さないleafが混じる） | 保たれる |
| 「一時的でレイアウトの外に浮く画面」という要件との適合 | 低い | 高い |
| 昇格時の実装イメージ | Tile内で種別変更 | 別状態からTileへ編入 |

同時に開ける数・状態のスコープ:

| 観点 | a. アプリ全体で1つ | b. ワークスペースごとに1つ | c. ワークスペースごとに複数 |
|------|---------------------|------------------------------|--------------------------------|
| 状態管理・UXのシンプルさ | 高い | 高い | 低い（一覧・選択UIが要る） |
| ワークスペース切り替え時の直感的な挙動 | 低い（他ワークスペースの作業中にポップアップが割り込む） | 高い（ワークスペース＝独立した作業コンテキストという既存方針に合う） | 高い |
| 想定している要件（fzf・lazygit等の単発用途）との適合 | 過剰でない | 十分 | 過剰 |

## Decision

**ポップアップは、Workspace ごとに最大1つだけ持てる、Tile 木構造とは独立した一時的な状態として位置づける。**

### 1. データモデルの採用理由

Tile 木構造は「レイアウトを敷き詰める領域」を表す概念であり（ADR 0001）、ポップアップは意図的にレイアウトの外に浮く一時的な画面であるため、Tile 木に組み込まず、Workspace 直下の独立した状態として持つ方が既存の概念定義と一貫する。ただし「タブへ昇格」の要件を満たすため、ポップアップが保持する PTY セッションは、通常の Tab が保持するセッションと同じ実体として扱える設計とし、昇格時にセッションを作り直さず既存の Tile 配下へ編入できるようにする。

### 2. 同時開放数・スコープの採用理由

tmux の `display-popup` と同様に「今開いているポップアップは1つだけ」という単純なメンタルモデルを採用する。スコープをワークスペースごとに独立させることで、ワークスペースを切り替えても他ワークスペースのポップアップに割り込まれることがなく、「ワークスペースは独立した作業コンテキスト」という既存方針（ADR 0001）とも整合する。

## Consequences

### Positive

- 「タブへ昇格」が、PTY セッションの再生成なしに既存の Tab 管理へ編入するだけで実現でき、昇格前後で接続が途切れない
- ワークスペースごとに状態が独立するため、複数ワークスペースを行き来するワークフローでも挙動が予測しやすい
- Tile / Tab の既存概念（ADR 0001）を変更せずに済む

### Negative

- Tile 木構造の外側に状態を持つため、タイル・タブの一覧を前提にした既存の CLI コマンドやサイドバー表示のロジックに、ポップアップ用の分岐を別途追加する必要が生じる
  - → 影響箇所は実装に着手するセッションで洗い出し、対応を加える
- 同時に1つ・ワークスペースごとという制約により、「ワークスペースをまたいで使い回すポップアップ」「複数ポップアップの並行使用」には対応できない
  - → 想定している用途（fzf・lazygit等の単発操作）では不要と判断。要求が具体化した時点で改めて検討する

### Risks

- 同時1つという制約は、将来 tmux の floating window のような「複数の浮動画面を並べる」要求が出た場合、状態管理を作り直す必要が生じる可能性がある
  - → 現状想定している要件（一時的なコマンド実行のための単一画面）では十分と判断し、複数化の要求が具体化してから再検討する

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| 表示レイヤーの実現技術（別ウィンドウ／別webview(OOPIF)／既存webview内のDOM等） | 実装上の選択であり、将来の実装都合で変わりうる。本ADRは「popupが何であるか」のみを扱う | 実装セッション |
| ポップアップの画面サイズ・配置の指定方法（パーセント指定か行数指定か、位置は中央固定かなど） | UXの細部であり実装時に決めても手戻りが少ない | 実装セッション |
| CLI・IPC・キーバインドの具体的なコマンド名・引数・デフォルトキー | 実装詳細であり本ADRのスコープ外 | 実装セッション |
| ワンショットコマンド実行時の起動方式（シェル経由かPTYへ直接execか） | 実装詳細であり本ADRのスコープ外 | 実装セッション |
| ポップアップの位置指定（tmuxの`-x`/`-y`相当） | 現状の要件に含まれておらず、中央固定で十分と判断 | 要望が具体化したとき |
