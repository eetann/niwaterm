# ADR 0006: Workspace と Tile の間に Board 階層を追加する

## Status

Accepted

## Context

niwaterm は Window > Workspace > Tile > Tab の4階層で画面構成を表現しており（ADR 0001）、Workspace は案件・プロジェクト単位のコンテナとして、切り替えるとタイルレイアウトごと入れ替わる。この定義に沿って、実装上も1つの Workspace は単一の Tile ツリーを直接保持している（`src/bun/workspace.ts`）。

一方で実際の作業では、1つの案件（Workspace）の中でも複数のリポジトリを並行して触ったり、同じリポジトリで複数の Git ワークツリーを同時に作業したりする。「案件1」という Workspace の中で、複数のリポジトリ（「リポジトリA」「リポジトリB」）や、同じリポジトリの複数のワークツリー（「ワークツリー1」「ワークツリー2」）を、それぞれ独立したタイルレイアウトとして切り替えながら使いたい。この要求は ADR 0001 の「決めていないこと」に「Workspace をさらに束ねる概念（cmux の Workspace Groups 相当）」として先送りされていた。

tmux でいう Window（1つのレイアウトをまるごと切り替える単位）に相当する概念だが、niwaterm では候補になりそうな語がどれも別の意味で先取りされていて使えない。

- **Window**: OS ウィンドウの呼称として最上位階層に使用済み
- **Session**: ADR 0001 で「永続化・IPC サーバーの名前空間の文脈に温存する」と明記済み
- **Layout**: `niwaterm layout apply`（設定ファイルに書いたレイアウトを名前指定で適用する既存機能）で、既に別の意味に使用済み

### 解決したい課題

- 1つの Workspace 内で、複数の独立した Tile レイアウトを持ち、切り替えられるようにする
- 新階層を Workspace と Tile のどちらの役割に近づけるか（Workspace の定義自体を変えるか、間に挟むだけにするか）を決める
- 新階層の名前を、既存の語（Window / Session / Layout）と衝突しない形で決める

### 検討した選択肢

**階層をどこに挟むか:**

- a. Workspace の定義を「1つのレイアウトセット」に変更し、現在の Workspace（案件単位）は新しい上位概念に置き換える
- b. Workspace の定義は変えず、Workspace と Tile の間に新階層を1枚追加する

**新階層の名前:**

- Room / Group / Board

### 各選択肢の評価

階層をどこに挟むか:

| 観点 | a. Workspaceを再定義 | b. 間に1枚追加 |
|------|----------------------|------------------|
| 既存のWorkspace定義（案件単位のコンテナ、ADR 0001）との整合 | 崩れる。Workspaceの意味自体が変わり、サイドバー・CLI・永続化スキーマの呼称も見直しになる | 保たれる。既存のWorkspace関連コード・ドキュメント・CLIコマンドはそのまま活かせる |
| ユーザーの要望との対応 | 案件単位の概念に新しい名前を用意し直す必要がある | 「案件」=Workspace、「リポジトリ/ワークツリー」=新階層と、要望のたとえ話にそのまま対応する |
| 変更コスト | 高い（型・RPC・CLI・永続化・サイドバー全域の呼称変更） | 中程度（新階層の追加が中心で、既存Workspace周りは無改修） |

新階層の名前:

| 観点 | Room | Group | Board |
|------|------|-------|-------|
| 空間的なイメージの伝わりやすさ | 高い（Workspaceという大部屋の中の小部屋） | 低い（「グループ化する」という操作寄りの語感） | 中（タイルを敷き詰める板というイメージ） |
| 既存語彙との衝突 | なし | ADR 0001で分割領域（Tile）の候補として一度検討済みだが不採用。階層名としては未使用 | なし |
| Tileとの関係の伝わりやすさ | 低い（部屋の比喩は「タイルを敷き詰める」イメージと接続しない） | 中 | 高い（板の上にタイルを敷き詰めるという構造がそのまま名前に出る） |

## Decision

**Workspace の定義は変えず、Workspace と Tile の間に Board という新階層を追加する。1つの Workspace は複数の Board を持ち、Board を切り替えると Tile レイアウトがまるごと入れ替わる。**

```
Window（OSウィンドウ。当面1つ）
└─ Workspace（案件・プロジェクト単位のコンテナ）
   └─ Board（Tileレイアウトをまるごと切り替える単位。複数のリポジトリ・ワークツリー等）
      └─ Tile（分割領域）
         └─ Tab（PTY等を保持する末端）
```

### 1. 「間に1枚追加」を採用した理由

上の比較のとおり、この案は Workspace の定義（ADR 0001で確定した「案件単位のコンテナ」）を変えずに済む。既存のサイドバー・CLI・永続化まわりのコードとドキュメントも、そのまま活かせる。ユーザーが実際に求めている単位も、Workspace=案件、Board=リポジトリ/ワークツリーという対応でそのまま一致する。

### 2. Board という名前を採用した理由

Room・Group も候補に挙がった。決め手は「タイルを敷き詰める板」という空間イメージで、これが Tile との親子関係をもっとも素直に表す。Room は部屋という比喩が Workspace との上下関係の説明には効くものの、その下に Tile が敷き詰められるという構造とは結びつかない。Group は分割領域（Tile）の候補として ADR 0001 で一度検討された語で、階層名としては未使用だが、語感が操作寄りで空間を想起させにくい。

### 3. Tile ツリーとの対応

実装上、現在1つの Workspace が直接持っている単一の Tile ツリーは、複数の Board それぞれが1本ずつ持つ形に置き換わる。具体的には `src/bun/workspace.ts` の `tree: TileNode` を、Board ごとの Tile ツリーへ分ける形になる。Tile・Tab の定義（ADR 0001）自体は変更しない。

### 4. ポップアップ（ADR 0005）との関係

ポップアップは ADR 0005 で「Workspace ごとに最大1つ」と定義されている。fzf・lazygit 等の一時的な単発操作という用途では、Board をまたいでも同じポップアップを使えたほうが自然である。そのため、ポップアップのスコープは Board 単位にはせず、Workspace 直下のまま変更しない。

## Consequences

### Positive

- 「案件（Workspace）の中で複数のリポジトリ・ワークツリーを並行して扱いたい」という要望に対応できる
- Workspace・Tile・Tab の既存定義（ADR 0001）は変わらない
- 変更範囲を Board の追加に限定できる
- サイドバーで「Board が1つしかない Workspace は Board の見出しを省略する」といった最適化を入れれば、Board を使わない既存ユーザーの見え方をほぼ変えずに済む

### Negative

- Workspace > Tile > Tab の3段だったネストが Workspace > Board > Tile > Tab の4段になり、型定義・RPC（NiwaRPC）・永続化スキーマ・サイドバーの折りたたみ構造・CLI コマンドなど、Workspace 関連の実装全体に影響する変更になる
  - → 影響範囲は実装に着手するセッションで洗い出す
- サイドバーの階層が1段深くなるため、Board を使わないユーザーには見た目が煩雑になりうる
  - → 上記の「Boardが1つのみの場合は見出しを省略する」表示で緩和する

### Risks

- Board 導入により Tile ツリーの持ち方が「Workspace が1本」から「Board ごとに1本」に変わるため、既存の永続化データ（`workspaces.json`）との整合を取るマイグレーションが必要になる
  - → 実装セッションで、旧形式（Workspace 直下に1本の layout）を「Board が1つだけの Workspace」として読み替える変換を用意する

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| Board型の具体的なフィールド名・データ構造 | 実装詳細でありADRのスコープ外 | 実装セッション |
| CLIコマンド（`niwaterm board new`等の具体的な引数） | `.claude/rules/cli-command-naming.md`の規則に沿って実装時に設計する | 実装セッション |
| サイドバーでのBoard切り替えUI（見出しクリックか、専用のタブバーか） | UIの細部であり実装時に決めても手戻りが少ない | 実装セッション |
| 既存永続化データのマイグレーション処理の具体的な実装 | 実装詳細 | 実装セッション |
| `niwaterm layout apply`とBoardの関係（レイアウト適用先をBoard単位にするか） | 既存機能との統合はBoard導入後、使用感を見てから判断する | Board実装後 |
