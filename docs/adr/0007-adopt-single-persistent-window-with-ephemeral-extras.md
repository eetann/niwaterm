# ADR 0007: 複数ウィンドウは「復元するメイン1枚＋使い捨ての一時ウィンドウ」とする

## Status

Accepted

## Context

ADR 0001 で画面構成を Window > Workspace > Tile > Tab の4階層と定めたが、Window の複数対応は「必要になったとき」に先送りしていた。実装も Window 層を持たず、`BrowserWindow` 1枚と `WorkspaceManager` 1つがトップレベルに置かれた「OSウィンドウ1枚」前提になっていた。

複数ウィンドウが欲しくなる場面は、常用しているレイアウトを崩さずに、別のディスプレイやサブ画面で一時的な作業をしたいときである。ここで「2枚目のウィンドウの状態をどう扱うか」を決める必要がある。

### 解決したい課題

- 2枚目以降のウィンドウの中身を、終了時に保存して次回起動時に復元するかどうかを決める
- 復元するなら、どのウィンドウの中身をどの順で復元するのか（ディスプレイ構成が変わった場合を含む）を決める
- 既存の永続化（`workspaces.json`・`window.json`）をどう拡張するか、あるいは拡張しないかを決める

### 検討した選択肢

- a. 全ウィンドウを復元する（ターミナルマルチプレクサ的。エディタのウィンドウ復元にも近い）
- b. メインウィンドウだけ復元し、2枚目以降は復元しない（ブラウザの新規ウィンドウ的）

### 各選択肢の評価

| 観点                                       | a. 全ウィンドウを復元                                                                                              | b. メイン1枚だけ復元                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 一時的な作業のための2枚目という用途との相性 | 悪い。使い捨てのつもりで開いたウィンドウが次回も開き、閉じて回る手間が残る                                          | 良い。開いて使って閉じれば何も残らない                                    |
| ディスプレイ構成が変わったときの復元        | 難しい。ウィンドウごとに枠の妥当性判定が要り、外部ディスプレイを外した状態では画面外への復元・重なりが起きやすい    | 既存の1枚ぶんの判定（`window-state.ts`）がそのまま使える                 |
| 永続化スキーマへの影響                      | `workspaces.json`・`window.json` の両方をウィンドウの配列へ拡張する必要があり、移行が要る                          | 変更不要。どちらも「メインウィンドウ1枚ぶん」のままでよい                 |
| 「どのウィンドウが本体か」の曖昧さ          | 残る。復元順・フォーカス・どれを閉じると終了かの規則を別途決める必要がある                                          | 無い。本体は常にメインウィンドウ1枚                                       |

## Decision

**ウィンドウを2種類に分け、状態を復元・保存するのはメインウィンドウ1枚だけとする。**

### 1. 2種類のウィンドウ

| 種別           | 枚数       | 起動時                                             | 終了時                                     |
| -------------- | ---------- | -------------------------------------------------- | ------------------------------------------ |
| メインウィンドウ | 常に1枚   | `workspaces.json` の中身と `window.json` の枠を復元 | 中身と枠を書き戻す                         |
| 一時ウィンドウ   | 0枚以上   | 起動時には開かない。まっさらな1タブで開く           | 何も書き出さない（閉じた時点で跡形もない） |

一時ウィンドウの枠は保存せず、既定の枠を開いている枚数ぶんずらして重ねる。

### 2. アプリの終了条件

**全ウィンドウが閉じたときにアプリを終了する**（ブラウザと同じ）。メインウィンドウを先に閉じても、一時ウィンドウが残っていればアプリは生き続ける。このときメインウィンドウの中身はメインウィンドウを閉じた時点の内容で確定し、以降 `workspaces.json` は更新しない。一時ウィンドウの中身で前回の状態を上書きしないためである。

### 3. ウィンドウ1枚につき WorkspaceManager 1つ

```
WindowManager（新設・src/bun/window-manager.ts）
├─ window-0 (persistent) → WorkspaceManager → Workspace > Board > Tile > Tab
└─ window-1 (temporary)  → WorkspaceManager → Workspace > Board > Tile > Tab
```

`WorkspaceManager` を Window ごとに持ち、`WindowManager` が id から持ち主のウィンドウを引いて委譲する。**`WindowManager` は `WorkspaceManager` と構造的に互換な型を持つ**ため、id を指定して操作する既存コード（`ipc-server.ts`・`niwa-api.ts`・`layout-apply.ts`）は呼び出し側を変えずに複数ウィンドウへ対応する。

採用理由は、一時ウィンドウの「保存しない」がマネージャを永続化対象から外すだけで済み、ウィンドウを閉じる処理もマネージャごと破棄するだけで済むこと。単一の `WorkspaceManager` に Window 次元を持たせる案は、ワークスペースの並び・アクティブ・ポップアップの持ち主といった状態すべてをウィンドウ単位へ分解する必要があり、既存の実装とテストに広く手が入る。

この構成が成り立つ前提として、**tile/tab/board/workspace の id はアプリ全体で一意**にする（採番はウィンドウ間で共有する）。CLI・RPC は id だけで対象を指すため、ウィンドウごとに採番すると別ウィンドウの同番 id を掴んでしまう。

### 4. 「今のウィンドウ」の決め方

対象 id を取らない操作（`workspace new`・`popup open`・フォーカス移動など）には宛先のウィンドウが要る。CLI は全リクエストに呼び出し元タブの id（`NIWATERM_TAB_ID`）を添えて送り、**そのタブが載っているウィンドウ**を宛先にする。niwaterm の外から実行された場合は最後にフォーカスされたウィンドウへ落とす。

## Consequences

### Positive

- 一時ウィンドウは開いて閉じるだけで完結し、次回起動時の状態を汚さない
- 永続化スキーマ（`workspaces.json`・`window.json`）を一切変えずに複数ウィンドウへ対応できる
- ディスプレイ構成が変わったときの復元の難しさが、従来と同じ「1枚ぶん」に留まる

### Negative

- 2枚目以降のレイアウトを作り込んでも次回に持ち越せない
  - → 作り込んだレイアウトは Board のレイアウトプリセット（ADR 0006・`layout apply --startup`）として残し、必要なウィンドウで呼び出す
- 一時ウィンドウを閉じるとその中の PTY はすべて終了する。メインウィンドウを閉じるのと違い「後で戻す」手段が無い
  - → 閉じるのは OS のクローズ操作と `window close` だけで、キーバインドからの誤爆経路は作らない
- ウィンドウをまたいだタブ・Board の移動ができない（マネージャが別のため）
  - → 移動したい中身はメインウィンドウ側に置く運用になる。必要になったら別途対応する

### Risks

- ウィンドウをまたぐ操作（`tab focus` で別ウィンドウのタブを指す等）で、どのウィンドウを前面に出すかの判断が要る
  - → タブの持ち主のウィンドウを前面に出す。id から持ち主を引く経路は `WindowManager` に一本化する
- Windows のウィンドウ透過（`src/native/winwindow.c`）は自プロセスの最初のウィンドウ1枚だけを処理する実装だった
  - → 未処理のウィンドウすべてを対象にし、差し替え前のウィンドウプロシージャをウィンドウごとに保持するよう変更した

## 決めていないこと

| 項目                                       | 決めない理由                                                                               | いつ決めるか                     |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------- |
| ウィンドウをまたいだタブ・Board の移動     | PTY と webview の載せ替えが要り、複数ウィンドウそのものの需要を満たしてから判断したい       | 移動したいという要求が出たとき   |
| メインウィンドウを2枚以上持てるようにするか | 「本体は1枚」という曖昧さの無さが本ADRの価値であり、崩す必要が生じていない                 | 複数の常用レイアウトが必要なとき |
| ウィンドウごとのフォントサイズ・設定の分離 | 設定はアプリ全体で1つという既存の前提を崩す理由が無い                                      | ウィンドウ別の設定要求が出たとき |
