# ADR 0008: ユーザー向けドキュメントはdocs/guideをやめ、ドキュメントサイトのMarkdownを正本にする

## Status

Accepted

## Context

ADR 0002では`docs/`配下を1つのOKFバンドルとして扱い、ユーザー向けのリファレンス（`type: Reference`）を`docs/guide/`に置くと決めた。現在`docs/guide/`には`cli.md`・`config.md`・`worktree.md`の3ファイルがあり、`niwaterm docs show <name>`はこのディレクトリを走査して内容を表示している（AIエージェントもniwaterm-cliスキル経由でこれを読む）。

一方で、開発者向けツールによくある形のユーザー向けドキュメントサイトを作ることになった。トップページで機能を紹介し、導入方法や設定ファイルの書き方を内容ごとのページに分けて載せるもので、GitHub Pagesでの公開を想定している。サイトはドキュメントフレームワークでMarkdownから生成する。

ここで、`docs/guide/`とサイトのページのどちらを正本にするかを決める必要がある。

### 解決したい課題

- ユーザー向けドキュメントの正本を1か所に決め、内容の二重管理を避ける
- `config.md`は1500行を超えている。サイトでページ単位に分割したとき、分割後のファイル構成とサイドバーの構成を一致させたい
- `niwaterm docs show`とサイトとで、同じ内容を見せたい

### 検討した選択肢

- A: `docs/guide/`を正本のまま残し、サイトはビルド時にそこからMarkdownを取り込む
- B: サイト側に独立して書き、`docs/guide/`はCLI・AIエージェント向けとして別に残す
- C: `docs/guide/`を廃止し、サイトのcontentディレクトリのMarkdownを正本にする。`niwaterm docs show`もそこを読む

### 各選択肢の評価

| 観点 | A: guideを正本に取り込む | B: 別々に書く | C: サイト側を正本にする |
|------|------|------|------|
| 内容の二重管理 | なし | あり（同期漏れが起きる） | なし |
| ページ分割とサイドバー構成 | フレームワーク外のファイル配置をサイト構成へ写像する仕組みが要る | 自由 | フレームワークの規約どおりに置ける |
| frontmatter | OKFとフレームワークの両方の要件を満たす必要がある | 別々 | フレームワークの要件だけで済む |
| `docs show`との一致 | 一致 | 同期しない限りずれる | 一致（読み込み先の変更が要る） |
| 仕組みの複雑さ | 取り込み処理を自前で持つ | 単純 | 単純 |

## Decision

**`docs/guide/`を廃止し、ユーザー向けドキュメントはリポジトリ直下の`website/`に置くドキュメントフレームワークのcontentディレクトリへMarkdownとして書く。そこを唯一の正本とし、`niwaterm docs show`もそこを読む。**

### 1. 置き場所と読み手の分担

```
docs/        # OKFバンドル。開発者・AIエージェント向け（planning/ build/ adr/ known-issues/）
website/     # ドキュメントサイト。niwatermを使うユーザー向け
  (フレームワークのcontentディレクトリ)/
    *.md, *.mdx
```

- `docs/`は「niwatermを開発する人」向けに絞る。ADR 0002 §7で`guide/`と`build/`の境界にしていた「使う人かビルドする人か」は、今後は`website/`と`docs/`の境界になる
- `website/`を`packages/`配下に置かないのは、`packages/*`がnpmパッケージとして公開・参照される単位であり、サイトはそうではないため

### 2. ページはMarkdownで書く

本文は`.md`で書く。フレームワークのコンポーネント（トップページのカード並びなど）が必要なページだけ`.mdx`にする。`niwaterm docs show`はファイルの中身をそのまま標準出力へ書くため、`.mdx`のページはターミナルで読みにくくなる。リファレンス類は`.md`のままにしておく。

### 3. サイトのページはOKFバンドルの対象外にする

`website/`は`docs/`の外にあるので、ADR 0002のOKFの規約（`type`必須、バンドル相対パスのリンク）は適用しない。frontmatterはフレームワークの規約に従い、そのうえで`title`と`description`を必須とする。`description`は`niwaterm docs list`がトピックの説明として表示するので、省略できない。

ページ間のリンクはフレームワークのURL規約に従う。`docs/`側からサイトのページを参照するときは、`website/`配下のファイルパスで書く。

## Consequences

### Positive

- ユーザー向けドキュメントの正本が1か所になり、サイトと`docs show`で内容がずれない
- ページの分割・並べ替えをフレームワークの規約どおりに行え、ファイル構成とサイドバーが対応する
- `docs/`が開発者・AIエージェント向けだけになり、OKFバンドルとしての性質がはっきりする

### Negative

- CLIの`docs show`が`website/`の配置規約に依存する。フレームワークのcontentディレクトリの場所が変わると、CLIも追従しなければならない
  - → 読み込み先のパスはCLI内の1か所にまとめる。`docs.test.ts`でトピックが1件以上取れることを確認し、配置が変わったらテストで気づけるようにする
- ユーザー向けドキュメントがOKFの`type`を持たなくなり、AIエージェントが`docs/`だけを見てもユーザー向けの情報にたどり着けない
  - → AGENTS.mdにユーザー向けドキュメントの場所を書き、AIエージェントには`niwaterm docs list`/`show`を使ってもらう

### Risks

- サイトを公開する前は、ユーザーが読めるのはGitHub上の`website/`配下のMarkdownか`docs show`だけになる。`.mdx`やフレームワーク固有の記法が増えるほど、これらでは読みにくくなる
  - → 2.のとおり、リファレンス類は`.md`で書く

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| サブディレクトリに分けたページのトピック名（`config/keybindings`のようなパス形式にするか等） | ページの分割案がまだ固まっていない | `docs/guide/`をサイトへ移すとき |
| `website/`をoxlint・oxfmtの対象に含めるか | `.astro`・`.mdx`への対応状況を確認していない | サイトの雛形を作るとき |
| 公開方法（GitHub Pagesの有効化、デプロイの仕組み） | リポジトリがprivateで、公開の方針が決まっていない | リポジトリの公開か配布物の準備ができたとき |
