# Claude Codeは作業中にもBELを鳴らす

## 症状

Claude Codeを動かしているタブで、まだ普通に作業が続いている最中に
タブバー・サイドバーへベルのマークが出て、デスクトップ通知が飛ぶ。
応答が返ってきたわけでも、権限確認で止まっているわけでもない。

## 原因

**Claude Codeが本物のBEL文字（`0x07`）を出している。** niwaterm側のVTパーサの誤検知ではない。

紛らわしいことに、Claude CodeはTUIのタイトル更新（`OSC 0`）を1秒ごとに送っており、
その終端にもBELを使う（`\x1b]0;◐ …\x07`）。こちらはlibghostty-vtが正しくOSCの終端として
食べるのでベルにはならない。実際にベルとして鳴るのは、それらとは別に単独で出てくるBELで、
PTYの生バイト列を録って数えると**長いコマンドの実行が一定時間（実測で最後のユーザー操作から60秒）を
超え、画面に「still running」が出る瞬間**に1回鳴る。

つまりClaude Codeのベルは「手が要るようになった合図」ではなく「まだ終わっていない合図」であり、
ベルの本来の用途（長いビルドの終わりを別のタブから拾う）と意味が逆になっている。
応答完了時・権限確認時にはBELを出さないことも実測で確認している。

## 対処

既定のベル処理（`niwa-api.ts`の`defaultBell`）は、タブ変数`agent_status`が`working`の間に
鳴ったベルをマークも通知もせず捨てる。エージェントの状態は
[エージェント統合](/guide/cli.md)のhooksがタブ変数として書き込んでいるので、
ベルが鳴った時点でそのタブのエージェントが作業中かどうかが分かる。

手が要る場面（権限確認・応答完了）では`agent_status`が`blocked`・`idle`へ変わり、
サイドバーのバッジで分かるため、ベルを捨てても取りこぼしにはならない。

hooksを入れていないタブでは`agent_status`が無く、この間引きは働かない（従来どおりの挙動）。
逆に、Claude Codeを強制終了して終了hookが走らなかったタブでは`agent_status`が`working`のまま
残るため、そのタブのベルは以後すべて捨てられる。サイドバーの「作業中」バッジも同時に残るので、
表示が実態とずれていることには気づける。
