# Windows実機: CSS transformの拡大がグリフの大きさに反映されない（ppemの整数丸め）

## 症状

`█`を縦に並べたとき、macOSでは隙間なく繋がるのに、Windows実機では行の境目に
1px弱の隙間（地の背景色）が残る。罫線の`│`も破線のように途切れる。

`.cell-glyph`のCSS変数（`--cell-glyph-scale` / `--cell-glyph-shift`）は正しく計算されており、
`getComputedStyle`でも`matrix(1, 0, 0, 1.03659, 0, 0.378049)`と期待どおりの値が入っている。
要素の`getBoundingClientRect().height`も倍率どおり18.66pxへ伸びている。にもかかわらず、
**描かれるグリフの大きさだけが変わらない**。

## 根本原因

Windows(Chromium/DirectWrite)は、グリフをラスタライズする解像度(ppem)を整数へ丸める。
transformのスケールはppemの決定に使われるが、丸めの結果が同じ整数へ落ちる限り、
出来上がるグリフのビットマップは完全に同一になる。位置決め（advance・平行移動）は
小数のまま効くので、要素は伸びているのにグリフだけ伸びない、という挙動になる。

実機で測ったHackGen Console NFの`█`のインク高（font-size 13px・dpr 1）:

| 指定font-size | 実際のppem | インク高 |
| ------------- | ---------- | -------- |
| 13.0px        | 13         | 17.36px  |
| 13.4756px     | 13         | 17.36px  |
| 13.6px        | 14         | 19.0px   |
| 14.0px        | 14         | 19.0px   |
| 15.0px        | 15         | 20.18px  |

行の高さ18pxを埋めるには理論上1.0366倍で足りるが、13×1.0366=13.4756pxはppem 13へ丸められ、
インク高は17.36pxのまま＝0.64pxの隙間が残る。macOS(WebKit/CoreText)はこの丸めを行わないため、
同じコードでも隙間なく繋がる。

なお`measureText`の`actualBoundingBoxAscent/Descent`もWindowsではピクセルグリッドへ切り上げた
整数で返る（実測13.36pxのインクが14pxと報告される）ため、こちらもインク高の測定には使えない。

## 対処

「理論値で倍率を決める」のをやめ、**実際にラスタライズして測りながら倍率を探す**
（src/mainview/index.ts の`measureCellGlyphInk` / `findCellGlyphFill`）。

- インク高はcanvasへ`█`を描いてピクセル走査で測る。端の行の被覆率から小数の端まで復元する
- 理論値の倍率から始め、実測のインク高が行の高さに届かなければフォントサイズを少しずつ上げて
  測り直す。canvasのラスタライズもDOMと同じ丸めをするので、丸めの有無に関わらず
  「行の高さを埋められる最小の倍率」へ収束する
- 丸めで1段階大きいグリフ（ppem 14 = インク高19px）になった場合は行の高さを1px超えるので、
  はみ出す分を上下へ均等に振って行の中心とインクの中心を合わせる

副作用として、Windowsでは罫線・ブロック文字だけが1段階大きいppemで描かれる（advanceは
font-size 13pxのままなので桁はズレない）。隣接セルへ0.5px程度はみ出すが、
セルを埋める前提の文字なので見た目には現れない。

## 調べ方のメモ

倍率が効いているかどうかは、スクリーンショットのピクセル値を直接読むのが確実。
`█`を並べた行の縦1列を切り出して走査すると、隙間の被覆率が数値で分かる。

```sh
ffmpeg -i shot.png -vf "crop=1:120:<x>:<y>" -f rawvideo -pix_fmt rgb24 col.raw
```

「17行が完全被覆＋1行が0.365被覆」のように**周期がインク高と一致していれば拡大されていない**。
倍率を1.03と1.0366のように変えても隙間の被覆率が1ピクセルも変わらなければ、ppemの丸めを疑う。
