# user-doc-writer

`website/src/content/docs/`のページは、niwatermを使う人が読む。読み手が最初に知りたいのは「どんな機能があるか」で、次に「どう使うか」。細かいオプションはその後でよい。内部の仕組みは知りたがっていない。

ファイルの置き方・frontmatter・ページ間リンクの書き方といった形式のルールは、doc-writerスキルの「ユーザー向けドキュメント（`website/`）」節が正本。このスキルは中身の書き方を扱う。

## 文章はnatural-japaneseスキルで整える

書いたら、natural-japaneseスキルを使って文章を整える。チェックは次の2つで、どちらも検出0件にする。

```sh
# natural-japaneseスキルのディレクトリで実行する
uv run scripts/lint.py --genre tech <ページの絶対パス>

# AIっぽい語（「効く」「走る」「部品」など）の検出
textlint-ai-ja <ページのパス>
```

## ページの組み立て

- **冒頭で、何ができるかを先に言う**。そのあとに、どこに書くか・どう開くかを書く。いきなり「関数」「引数」から始めると、内部実装の話だと誤解される
- **設定ファイルの話なら、冒頭でそう示す**（「設定ファイルの`xxx`で変える」）
- **最初の例は、後の節で詳しく説明する機能も入れておく**。例えばキーバインドの最初の例に`description`を入れておくと、「そういうことも書けるのか」と分かって安心できる
- **GUIとCLIの両方でできる操作は、サイドバーなどGUIの手順とCLIの手順を子セクションに分ける**。GUI派がCLIを読み飛ばせるようにする。両方に共通する注意は親の節に置く
- 項目やアクションの一覧が長くなるときは、独立したページにする（例: `keybindings/actions.md`）
- 開発・トラブルシュート用のもの（`niwa ping`など）は、ページの最後に置く

## 書かないこと

- **内部実装**（ファイル監視の仕組み、デバウンス、プロセス間通信など）。仕組みの理由を書きたいときは、ユーザーにとっての利点として書く
- **細かい挙動や条件の列挙**。確認が出る条件の一覧、止まる条件の表、状態が切り替わるタイミングの例外、検索の細かい挙動（smartcaseなど）、省略できないオプションの一覧など。何のための機能か・確認かが分かれば足りる
- **CLIのコマンドとオプションの一覧**。`--help`に任せる。書かないと分かりにくい挙動だけを書く
- **前の説明で足りる出力例・エラー出力の例**
- **見れば分かる注意書き**
- **今どきのターミナルなら当然の前提**（「CLIがあると何が嬉しいか」など）
- **対象外の環境向けの補足**（Windows 10未満など）
- **実際にはほぼない使い方**。特に「チームで共有」「チームでそろえる」。ターミナルの設定をチームで共有することはないし、画面の大きさも人によって違う
- **ユーザーが直接使わないもの**。ホバーボタンなどが内部で呼ぶだけのコマンドの説明など
- **tmuxとの比較**。tmuxを知らない人には通じない。例外はconcepts.mdの対応表だけ

## 言葉づかい

- 「既定」ではなく「デフォルト」と書く
- デフォルトの挙動は「デフォルトでは」と書き、変えられることが伝わるようにする（「ブランチは残る」→「デフォルトではブランチは残る」）
- 「敷く」のような比喩的な動詞は使わず、「表示する」のように直接書く
- 初見で分からない言い方は避け、どこで何をするのかを書く（「信頼すると答えるまで」→「`worktree new`などの実行時に出る確認で信頼するまで」）
- 似た単語（ワークスペース・ワークツリー・ワークスペース一覧など）が並ぶところでは、「ビルトインの」のような修飾で区別する
- 「レイアウト機能」と「起動時に元に戻す動き」のように紛らわしいものは、「デフォルトでは」などで区別する
- 注意書きは、どの場合の話なのか範囲をはっきり書く。範囲があいまいだと、必要以上に不安にさせる（「`url`でほかのページを開くと`handlers`を呼べる」→「カスタムビューとして表示したページだけ。ふつうのブラウザタブからは呼べない」）

## 書式

- 対象を並べるだけなら、表にせずリストで足りる
- 読み落とすと困る一文だけを太字にする。太字を増やしすぎない
- リポジトリ内のファイル（`contrib/`など）を案内するときは、GitHubのURLへのリンクにする。サイトの読者はリポジトリを手元に持っていない。ディレクトリは`https://github.com/eetann/niwaterm/tree/main/...`、ファイルは`.../blob/main/...`

## 例と画像

- **設定例は、実際の使い方に寄せる**。例えばシェルの設定なら、macOSはOS標準、WindowsはWSLのディストロ、のようにOSで分ける例にする
- **例はniwaterm-wipで動かして確かめる**。wipの設定ファイル（`%USERPROFILE%\.config\niwaterm-wip\niwaterm.config.ts`）に書いて試す。書き換える前にバックアップを取る。niwaterm-dailyは触らない
- **見れば分かる機能は、説明を並べるよりスクショを載せる**。wipを小さめのウィンドウ（1280x800くらい）にして撮る
  - 画像は`website/src/assets/`に置き、ページから`../../assets/<名前>.png`のように相対パスで参照する
  - トップページ用のスクショ（`website/public/screenshots/`）も、該当する機能のページに載せる。こちらは`/niwaterm/screenshots/<名前>.png`で参照する
  - altには、何が写っているかを書く
- Windows実機でのスクショの撮り方（キー操作の合成など）
  - 基本はwindows-gui-testingスキルを参照する
  - prefixキーの操作は、SendKeysだと届かないことがある。その場合はuser32の`keybd_event`で送る。送る前に、シェルのタイルをクリックしてフォーカスを移しておく
  - ウィンドウだけを切り出すときは、`DwmGetWindowAttribute(hwnd, 9)`で枠を取る。`GetWindowRect`だと、後ろのウィンドウが写り込む。先に`SetProcessDPIAware()`も呼ぶ

## 書いたあとの確認

1. natural-japaneseの2つのチェックで検出0件
2. `bun run format`、続けて`bun run format:check`
3. `cd website && bun run build`が通る
4. 見出しを変えたら、そのアンカーへ張っているリンクを`grep -rn "/niwaterm/<ページ>/#" website/src .agents packages/cli/README.md`で探して直す。消した節を`.agents/skills/`のSKILL.mdが案内していないかも確かめる
5. コマンドを説明するページを変えたら、`website/src/content/docs/cli.md`の索引のリンク先も合わせる
