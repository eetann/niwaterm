# コード内コメントの書き方

`src/`・`packages/`配下のソースコメント（JSDoc含む）のルール。対象読者はAIエージェント・人間問わず、
このリポジトリのコードを書く全員。

## 書いてよいのは3種類だけ

1. **JSDocで関数・型・フィールドの役割を短く書く**
2. **コードから読み取れないWHY**（なぜこの順序なのか、なぜこの値なのか、なぜ他の手段を採らないのか）
3. **パッと読んだだけでは分からない仕様**（複数ファイルにまたがる前提、外部ライブラリの癖、タイミング依存）

これ以外は書かない。コードを読めば分かることの言い換え（`// カウンタを1増やす`）も不要。

## タスク番号・マイルストーン番号を書かない

`.rrmap/`のタスク（`TASK-0001`）・マイルストーン（`MILESTONE-0001`）の番号をコメントへ書かない。
`.rrmap/`はタスクが溜まったら**まとめて削除することがある**ため、番号を書くと参照先を失った
文字列だけがコードに残る。docs/配下（`[[TASK-0001]]`のリンク含む）も同様。

```ts
// NG
// PTY起動をwebview側の実測cols/rowsが届くまで保留する（TASK-0047）

// OK
// PTY起動をwebview側の実測cols/rowsが届くまで保留する。固定値で先に起動すると、
// 直後のSIGWINCHを取りこぼすTUIが誤ったサイズのまま固着するため
```

「いつ・どのタスクで入れたか」はgitの履歴が持っている。コメントが持つべきなのは**今のコードの理由**。

## 「経緯」を書かない

「以前はこうだった」「〜というバグがあったので直した」「実機検証で発覚した」といった**過去の話**は
コメントに書かない。読み手が知りたいのは今なぜこうなっているかであって、そこへ至る道のりではない。

```ts
// NG
// 起動直後にresizeでサイズを送り直す旧実装だと、fzf等のTUIがポップアップ枠の半分程度の
// 高さのまま固着するバグがあった。実機で確認済み

// OK
// 実測サイズが判明してから起動する。起動がSIGWINCH到達に間に合わないTUIは、
// 取りこぼしたSIGWINCHが再送されないため誤ったサイズのまま固着する
```

経緯を残したいときの置き場所は以下。

- 技術選定・設計方針の判断 → `docs/adr/`
- ハマりどころ・外部ライブラリのバグ → `docs/known-issues/`
- 変更の背景 → コミットメッセージ

コメントからそれらへ導線を張るのは構わない（`// 詳細: docs/known-issues/xxx.md`）。ADR番号は
rrmapと違って安定した参照先なので、`ADR 0005`のような参照は書いてよい。
